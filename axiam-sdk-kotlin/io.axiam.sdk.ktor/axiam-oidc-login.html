axiamOidcLogin

fun Route.axiamOidcLogin(client: AxiamClient, redirectUri: String, store: OidcStateStore = MemoryOidcStateStore(), loginPath: String = "/login", callbackPath: String = "/callback", scope: String? = null, successRedirect: String? = null, allowReturnTo: (String) -> Boolean? = null, onSuccessWithCall: suspend (OidcTokenSet, OidcStateEntry, ApplicationCall) -> Unit? = null, onSuccess: suspend (OidcTokenSet, OidcStateEntry) -> Unit? = null)

"Login with AXIAM" Ktor glue (CONTRACT.md §12) — installs the login-redirect and callback routes on this Route, following the SAME per-SDK conventions as AxiamAuthentication: kept compileOnly-safe, exactly like that plugin — the SDK core (io.axiam.sdk.AxiamClient and the io.axiam.sdk.oidc package) compiles and passes tests with Ktor entirely absent from a consumer's classpath; only a consumer who imports this file needs the ktor-server-core dependency their own project adds.

This function performs NO token extraction and sets no SESSION cookie of its own: oidcExchange's result is delivered to the host application only through onSuccess / onSuccessWithCall, which is where the application establishes its OWN session (sign a cookie, write a session row, ...) — this SDK deliberately does not decide what "logged in" means for the host application. The one cookie it does set is the short-lived browser-binding cookie below.

Browser binding (CONTRACT.md §12.8 rule 1; contract 1.68, C7)

The login route sets a random 32-byte value as the HttpOnly, Secure, SameSite=Lax, Path=/ cookie __Host-axiam_oidc_bind (no Domain; Max-Age=600) and stores its SHA-256 on the state entry. The callback consumes the entry FIRST (so state stays single-use), then refuses with the same 401 it gives an unknown state — no code exchange, no success callback — unless the request presents a cookie whose digest matches (constant-time compare). Without this, an attacker who began a login and stopped before the callback could have a victim's browser load callback?state=…&code=… and complete the attacker's login in the victim's request (login CSRF; RFC 6749 §10.12). The cookie is cleared on every callback response. Where redirectUri is http: on a loopback host (localhost, 127.0.0.1, [::1]) a browser will not store a Secure cookie, so the name is axiam_oidc_bind and Secure is omitted — there only. Two sign-ins started concurrently in one browser: the later login replaces the cookie, so the earlier callback is refused and the user starts again.

Upgrade note. Entries saved by 1.3.x glue carry no digest and are refused at the callback (one in-flight sign-in per user fails once and restarts). A caller-supplied store must persist OidcStateEntry.bindingDigest and return it unchanged.

The store is what turns the two HTTP requests of a redirect flow into one login: oidcBegin produces state/nonce/codeVerifier on the login request, and only state survives the round trip through the IdP, so the other two must be parked somewhere the callback request can reach (§12.3 rule 1 — the core §12 operations store nothing themselves).

Parameters

client

the relying-party AxiamClient driving the flow (built with oidcClientId/oidcClientSecret configured)

redirectUri

the relying party's redirect URI — the public URL of callbackPath — replayed verbatim on the token exchange (the server compares the two)

store

where in-flight login state is parked between the login redirect and the callback; defaults to a fresh MemoryOidcStateStore (single-process only — a multi-instance deployment needs a shared store)

loginPath

the route path that redirects the browser to the IdP

callbackPath

the route path the IdP redirects back to

scope

requested scope; openid is added automatically when absent (§12.1 rule 4)

successRedirect

where to send the browser after a successful login, which the integrator configures and which therefore wins; falls back to the return_to query parameter captured at login time, then to a 200 JSON summary. return_to is followed only as a same-origin relative path (CONTRACT.md §12.8 rule 3; C6): it must start with a single /, not // or /\, and contain no \ or control character. It is checked when stored (a failing value is dropped) and again before redirecting (a stored value that fails is not followed). A dropped return_to is treated as if none had been given

allowReturnTo

optional predicate that may WIDEN the return_to rule — e.g. an allowlist of the application's other origins. Consulted at both points, and only for a value the default rule refuses; a predicate that throws accepts nothing. There is no default predicate: absolute URLs are never followed unless the integrator says so

onSuccessWithCall

like onSuccess but also receives the Ktor ApplicationCall that completed the sign-in, so the application creates its session on THAT request without ambient context (§12.8 rule 2). Runs after onSuccess when both are set; the old hook is kept so the published signature of onSuccess does not change. The hook must not send a response: the glue sends the outcome itself, and when the hook has already responded (call.response.isCommitted) it sends nothing further. A hook that throws gets the framework's error response, which still clears the binding cookie (the clearing header is set before the hook can run)

onSuccess

called with the validated token set once the exchange succeeds — the hook where the host application establishes its OWN session (sign a cookie, write a session row, ...). Receives the consumed OidcStateEntry too, so returnTo and any other data captured at login time is available. It runs only after the browser binding and the code exchange have both succeeded
